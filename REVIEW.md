# REVIEW.md

I reviewed the starter `app/main.py` and then ran the **original starter** against each suspected problem with a concrete
input (the "How you'd notice it" column is the input I used and what I observed). I also ran it with the server clock set
to UTC, because a container usually runs in UTC and my laptop runs in IST, which hides the time zone bugs.
Rule numbers (R1 - R10) are from `openapi.yaml`.

## Helpers

| #   | Where                  | What is wrong                                                                                                                                                                                                           | How you'd notice it                                                                                                | How I fixed it                                                                                                                                  |
| --- | ---------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `compute_late_minutes` | `punch_in.replace(hour, minute)` builds the shift start on whatever clock the datetime carries: UTC for a value read back from MongoDB, the server's local zone for `datetime.fromtimestamp`. Shift times are IST (R1). | 10:15:59 IST on a 09:30 shift, as a UTC datetime, returns `0`; expected `45`.                                      | `shift_bounds()` builds the shift start/end in IST for the attendance date; `calc_late_minutes()` subtracts aware datetimes.                    |
| 2   | `compute_late_minutes` | The grace is checked on **floored minutes** (`minutes > 10`), so anything from 10:00 to 10:59 after the start is "not late" (R2: strictly more than 10:00).                                                             | 09:40:01 on a 09:30 shift returns `0`; expected `10`. Same for 09:40:59.                                           | Compare whole **seconds**: late only if `seconds > 600`, then `late = seconds // 60`.                                                           |
| 3   | `compute_late_minutes` | Ignores overnight shifts: the start is put on the punch-in's own calendar day.                                                                                                                                          | Shift 22:00 - 06:00, punch-in 01:30 next day returns `0`; expected `210` (the record belongs to the previous day). | `attendance_date()` implements R1 (a punch-in before `shift_end` belongs to the previous day); `shift_bounds()` anchors the start on that date. |
| 4   | `compute_work_hours`   | Python `round()` is round-half-to-even on a binary float, not half-up (R4, R8).                                                                                                                                         | 9630 s (2.675 h) returns `2.67`, expected `2.68`; 450 s (0.125 h) returns `0.12`, expected `0.13`.                 | `round_half_up()` uses `Decimal` with `ROUND_HALF_UP`; hours are computed as `Decimal(seconds) / 3600`.                                         |
| 5   | `compute_overtime`     | No 30-minute minimum (R3).                                                                                                                                                                                              | Punch-out 10 minutes after shift end returns `10`; expected `0`.                                                   | `calc_overtime_minutes()` returns 0 below 30 whole minutes.                                                                                     |
| 6   | `compute_overtime`     | Subtracts a timezone-aware shift end from the punch-out. PyMongo's default client returns **naive** datetimes, so any record read back from the database crashes.                                                       | `TypeError: can't subtract offset-naive and offset-aware datetimes` (a 500 in an endpoint).                        | The client is `tz_aware=True` (item 9) and every datetime in the code is aware UTC.                                                             |
| 7   | `compute_overtime`     | Puts the shift end on the record's date even when the shift ends the next day (R1).                                                                                                                                     | Shift end 06:00, date 2026-07-06, punch-out 06:40 next day returns `1480`; expected `40`.                          | `shift_bounds()` adds one day to the end of an overnight shift.                                                                                 |
| 8   | `punch_in` / helpers   | Instants are not truncated to whole seconds (R1) and are returned as ISO strings, not epoch milliseconds.                                                                                                               | Punch-in at `...001999` returns `"2026-07-06T04:10:01.999000"`; expected an integer ending in `000`.               | `ms_to_dt()` drops sub-second parts; `dt_to_ms()` / `serialize_record()` return integer epoch ms.                                               |

## Setup, database and `/health`

| #   | Where              | What is wrong                                                                                               | How you'd notice it                                             | How I fixed it                                                                                                                                                                                           |
| --- | ------------------ | ----------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 9   | `MongoClient(...)` | Not `tz_aware=True`: PyMongo returns naive datetimes (see item 6), and no server-selection timeout is set.  | `punch_in.tzinfo is None` for every stored record read back.    | `MongoClient(uri, tz_aware=True, serverSelectionTimeoutMS=3000)`; conversion to epoch ms only at the API boundary.                                                                                       |
| 10  | whole app          | No index is created, so nothing enforces uniqueness (items 13 and 23) and every query is a collection scan. | `db.employees.index_information()` shows only `_id_`.           | `ensure_indexes()` runs at startup (retrying while MongoDB comes up) and `/health` retries it if startup could not: unique `emp_code`, unique `(emp_code, date)` plus the listing and analytics indexes. |
| 11  | `health`           | Returns 200 without touching MongoDB (the contract says 503 when it cannot answer).                         | Point the client at a dead port: `/health` still returns `200`. | `/health` pings MongoDB and returns 503 on failure; any endpoint that cannot reach the database also answers 503 instead of a traceback.                                                                 |

## Employees

| #   | Where             | What is wrong                                                                                                                                                                                       | How you'd notice it                                                                                                                                                                                                 | How I fixed it                                                                                                                                    |
| --- | ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------- |
| 12  | `EmployeeIn`      | No validation: any string is accepted.                                                                                                                                                              | `{"emp_code":"x","name":"","email":"nope","shift_start":"25:99","joined_on":"not-a-date"}` returns `201`; expected `422`.                                                                                           | `EmployeeCreate`: `emp_code` pattern, length limits, email pattern, `HH:MM` pattern, `joined_on` must be a real date, `shift_start != shift_end`. |
| 13  | `create_employee` | Check-then-insert (`find_one`, then `insert_one`) leaves a window between the check and the write, and nothing in the database prevents duplicates (no unique index).                               | The window is narrow here: 30 parallel creates did not trigger it in my run (the same pattern in punch-in, item 23, did). It is a race by construction: two requests can both pass the check before either inserts. | Unique index on `emp_code`; `insert_one` and catch `DuplicateKeyError` -> `409`. Verified with 30 parallel requests: one `201`, the rest `409`.   |
| 14  | `create_employee` | `created_at = datetime.now()` is local and naive, and it is returned as an ISO string instead of epoch ms (UTC).                                                                                    | Response shows `"created_at": "2026-10-11T13:04:18.464543"`.                                                                                                                                                        | `now_utc()` stores an aware UTC datetime; `serialize_employee()` returns epoch ms.                                                                |
| 15  | `list_employees`  | `skip = page * page_size` is off by one page (R10: page starts at 1).                                                                                                                               | `page=1&page_size=20` with 25 employees starts at the 21st employee.                                                                                                                                                | `skip = (page - 1) * page_size`.                                                                                                                  |
| 16  | `list_employees`  | `total` is `count_documents({})`, so it ignores the department filter (R10).                                                                                                                        | 12 employees in Sales, `department=Sales` reports `total: 25`.                                                                                                                                                      | `total = count_documents(query)` with the same filter.                                                                                            |
| 17  | `list_employees`  | `page` and `page_size` are unvalidated: `page_size=0` becomes `limit(0)`, which MongoDB treats as **no limit**; `page <= 0` gives a negative skip (PyMongo raises `ValueError`, a 500); no maximum. | `page_size=0` returns all 25 employees; `page=-1` -> skip -20 -> `ValueError: skip must be >= 0`.                                                                                                                   | `Query(1, ge=1)` for `page`, `Query(20, ge=1, le=100)` for `page_size` -> `422` (R10).                                                            |
| 18  | `list_employees`  | No sort, so the page boundaries depend on MongoDB's natural order.                                                                                                                                  | The query has no `.sort(...)`; paging over an unordered cursor can repeat or skip rows.                                                                                                                             | `.sort("emp_code", 1)`, served by the `(department, emp_code)` / `emp_code` indexes.                                                              |

## Attendance listing

| #   | Where             | What is wrong                                                                                                                                                                        | How you'd notice it                                                                                                                   | How I fixed it                                                                                                                                                                                     |
| --- | ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 25  | `list_attendance` | Loads **every** matching document into Python, sorts and slices there; no `skip`/`limit`/`sort` in the query. Cost and memory grow with the collection.                              | With 100,000 records, an unfiltered `GET /attendance` still reads all of them for a 20-row page.                                      | `find(filter).sort(...).skip(...).limit(...)` in MongoDB; `estimated_document_count()` for the unfiltered total; indexes match each filter shape. Checked with explain: `IXSCAN`, no `SORT` stage. |
| 26  | `list_attendance` | Sorts by `date` only; ties have no `emp_code` order.                                                                                                                                 | Three records on one date come back as `EMP0009, EMP0003, EMP0005`; expected `EMP0003, EMP0005, EMP0009`.                             | Sort `date` descending, then `emp_code` ascending (by `date` alone when `emp_code` is fixed, which is the same order).                                                                             |
| 27  | `list_attendance` | Nothing is validated: `page=0` slices `docs[-20:0]` (empty although `total > 0`); `date_from > date_to`, impossible dates, unknown `status` and a huge `page_size` all return `200`. | `page=0` -> `total: 3, items: []`; `date_from=2026-07-10&date_to=2026-07-01` -> `200`. Expected `422`.                                | `Query` constraints, real-date validation, a `Status` enum and a `date_from <= date_to` check -> `422`.                                                                                            |
| 28  | `list_attendance` | Returns documents as stored: `_id` exposed as `id`, legacy documents missing `history`, `half_day`, `late_minutes`, and raw datetimes.                                               | A seeded document without `history` comes back without the key (keys: `date, emp_code, id, punch_in, punch_out, status, work_hours`). | `serialize_record()` always returns the full contract shape: missing `late_minutes` / `overtime_minutes` -> 0, `half_day` -> false, `history` -> `[]`; epoch ms for instants.                      |

## Looked at and decided it is fine

- `load_dotenv()` with no arguments does **not** override variables that are already set, so real environment variables win over `.env`, which is what the contract needs. I kept it and made it explicit with `override=False`.
- Plain `def` endpoints with the synchronous PyMongo driver are fine: FastAPI runs them in a thread pool, and mixing blocking calls into `async def` would have been the mistake.
- `doc.pop("_id", None)` after `insert_one` correctly hides the id in `create_employee` (the insert adds `_id` to the dict). I replaced it with an explicit serializer only for consistency.
- The shape of the new punch-in document (`punch_out`/`work_hours` null, `overtime_minutes` 0, `half_day` false, `history` empty) matches `DATA_MODEL.md`; `status_code=201` on creation is right.
- `IST = timezone(timedelta(hours=5, minutes=30))` is correct, and anchoring the shift end on the date string with `tzinfo=IST` is right for day shifts (it breaks only for overnight shifts, item 7).
- Comparing `YYYY-MM-DD` strings with `$gte` / `$lte` in the attendance filter is correct, because ISO dates sort chronologically; I kept the approach.
